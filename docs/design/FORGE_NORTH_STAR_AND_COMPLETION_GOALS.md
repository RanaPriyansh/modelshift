# FORGE North Star and Completion Goals

Status: Active working direction.

Date: 2026-08-01.

## 1. Refined goal

Create one editable and implementation-linked FORGE Terrain product system.

The system must express the same learning contract across:

- The public website.
- The web application.
- Focus and protected proof.
- The native iOS application.

The final source must be useful for product review, visual iteration, implementation, and verification.

## 2. Product direction

The permanent visual rule is:

> Vivid at thresholds. Quiet during work. Precise when evidence appears.

The permanent trust rule is:

> Learner acts. AI assists. Evidence decides.

The permanent learning loop is:

```text
Recall -> Attempt -> Repair -> Prove -> Return
```

The product creates satisfaction through capability, useful feedback, closure, and later independent return.

The product does not use variable rewards, streak pressure, ranks, shame, or false urgency.

## 3. Experience goals

### G1. Clear agency

Each surface has one dominant learner action.

Each surface also provides a safe stop, exit, or recovery action.

### G2. Honest assistance

Learner work, AI contribution, and tested evidence use separate semantic treatments.

Protected proof removes instructional help.

Accessibility support remains available.

### G3. Memorable identity

Public thresholds use cobalt terrain, alpine green, ember orange, ivory, and midnight.

Work surfaces remain calm, legible, and structurally clear.

### G4. Cross-platform continuity

Public, web, focus, and iOS surfaces share the same states and evidence language.

Each platform uses native navigation and interaction structure.

### G5. Implementation parity

Figma names map to CSS variables and Swift identifiers.

Representative screens map to canonical route and screen identifiers.

## 4. Required editable source

The Figma file must contain:

1. Cover and product principles.
2. Light and Dark foundations.
3. Token variables with explicit scopes and code syntax.
4. Web and iOS text styles.
5. Environmental, authority, and elevation styles.
6. Reusable web components and state patterns.
7. Reusable iOS compounds.
8. Six representative public-site frames.
9. Six representative web-application frames.
10. Three representative focus frames.
11. Six representative iOS frames.
12. Shared loading, empty, offline, stale, permission, error, and recovery states.
13. Accessibility annotations.
14. Route and screen identifiers.
15. A canonical coverage index for all public, web, focus, and iOS families.

## 5. Completion gates

The design objective is complete only when all gates pass.

| Gate | Required evidence |
| --- | --- |
| Editable source | A working Figma URL with editable pages, variables, styles, components, and screens |
| Page inventory | Every canonical public, web, focus, and iOS family has an identifier and state contract |

| Design-system integrity | Variable, style, component, naming, and unresolved-binding audits pass |
| Web implementation | Representative public and application pages match the approved Figma direction |
| Responsive behavior | Desktop and 320 CSS pixel screenshots have no horizontal overflow |
| Themes | Light and Dark appearances preserve semantic meaning |
| Accessibility behavior | Keyboard, visible focus, Reduced Motion, and Forced Colors checks pass |
| iOS handoff | Native structure, Dynamic Type, VoiceOver order, Reduce Motion, and 44-point targets are specified |
| Provenance | Source revisions, screenshot hashes, test counts, and remaining external gates are recorded |

## 6. Current priority order

1. Preserve the audited Figma source, generator, token sources, identifiers, and coded atlas as one linked system.
2. Compare future Figma changes with the complete coded atlas.
3. Run the SwiftUI reference after a compatible iOS Simulator runtime is installed.
4. Test the design with representative learners.
5. Clear every image right before production use.

## 7. Execution direction

The design work follows three visual zones.

1. **Thresholds** use vivid landscapes, large typography, and one clear action.
2. **Work** uses quiet surfaces, strong hierarchy, and low visual noise.
3. **Evidence** uses precise labels, source state, assistance state, and proof boundaries.

The same system must work in Light and Dark appearances.

The public site can use the strongest environmental imagery.

The web application must give the learner more visual control than the environment.

The iOS application must use native navigation, controls, motion, and accessibility behavior.

No visual reward can replace useful learning feedback or independent evidence.

## 9. Boundaries

No local design evidence proves production operation, accessibility conformance, learning efficacy, or learner preference.

No image can enter production before its rights are cleared.

No native runtime claim is made until a simulator build and native checks pass.
